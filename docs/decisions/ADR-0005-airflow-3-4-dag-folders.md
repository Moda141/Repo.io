# ADR-0005 — Airflow 3.4 with DAGs organised in folders by domain and repository

- Status: **accepted** (2026-11-12, Mohamed)
- Amends:
  - README: technology table, §2.8 scheduling note, §6 module layout,
    §7.5 services, "Confirmed architecture decisions";
  - CLAUDE.md §4 technology table, §8 decisions list;
  - `docs/milestone-plan.md` §M2;
  - `docs/user-journey.md` J10 (job runs) and J15 (data sync);
  - skill `repoio-ingestion`.
- Does not change:
  - Airflow's role (pull ingest, DQ runs, housekeeping, broadcast
    dispatch);
  - the rule that DAGs never hold hosts or credentials (connections and
    the secret store, CLAUDE.md §6.10 and §6.13);
  - transformations living in `repoio-stream`, not in DAGs.

## Context

Airflow schedules every batch job in Repo.io:

- Data sync flows (one pull DAG per deployed replication flow, J15);
- scheduled data quality runs;
- housekeeping (Iceberg snapshot expiry, compaction, retention);
- connection health checks;
- broadcast dispatch (README §2.8).

The number of DAGs grows with every domain, repository and flow. In a
flat DAG list, operators cannot see which jobs belong to which
repository.

Apache Airflow **3.4.0** (released 2026-11-06) adds a **Folders panel**
to the Dags page. It groups DAGs by their directory layout inside each
DAG bundle, to any depth, with nothing to configure. Choosing a folder
filters the DAG list.

## Decision

1. **Airflow version.** Repo.io uses the **Airflow 3.4 line**.
   - The exact patch version is pinned when `repoio-airflow-apis` and
     `docker/` are scaffolded (M2), with Airflow's constraints file.
   - It is not upgraded as a side effect of other work (CLAUDE.md §6.7).
   - Before pinning, verify that the provider packages in use and the
     Python version (3.11, as for ingestion) are supported by that patch.
   - Features marked experimental in 3.4 (language SDKs, the Dag
     Importer framework, `common.ai` previews) are not used.
2. **Folder layout.** Every DAG file lives in a folder that mirrors the
   Repo.io hierarchy, so the Folders panel shows the same tree as the
   console:

   ```
   dags/
     <domain>/                    customer · vendor · product · author · employee · store
       <repository>/              repository technical name
         sync/<flow>.py           one DAG per deployed data sync flow
         dq/<suite>.py            scheduled data quality runs for the repository
     analytics/
       broadcasts/broadcast_dispatch.py
     platform/
       housekeeping/<job>.py      snapshot expiry, compaction, retention
       health/connection_health.py
   ```

   - Domain folders use the closed domain enum (README §3), in lowercase.
   - Repository and flow folders use **technical names**, which are fixed
     after the first save. Renaming a business name never moves a file.
   - A job that belongs to one repository always lives under that
     repository. Cross-cutting jobs live under `analytics/` or
     `platform/`; nothing sits loose at the root.
3. **DAG IDs and tags.**
   - **DAG ID:** the path joined with `__`, for example
     `customer__retail__sync__c4c_accounts`. This keeps IDs unique across
     repositories.
   - **Tags:** `domain:<d>`, `repo:<r>` and `kind:<sync|dq|housekeeping|broadcast|health>`,
     so that filters still work outside the Folders panel.
4. **DAG files generated by Deploy.** Deploying a data sync flow writes
   a thin DAG file to its folder from a reviewed template. The file holds
   only the flow ID. The flow definition and the connection reference are
   read from the control plane API at run time. They are not read at
   parse time, and no secrets are written into the file.
   - Hand-written DAGs (`platform/`, `analytics/`) ship from
     `repoio-airflow-apis` in Git.
   - Generated DAGs go to a separate bundle with the same layout. Both
     bundles show the same domain tree in the Folders panel.
   - The bundle mechanism is confirmed at M2 scaffolding: a Git bundle
     with commits from Deploy, or a shared volume.
5. **The console mirrors the layout.** Job runs (J10) and the Data sync
   list (J15) group and filter jobs by domain → repository → kind, using
   the same names. A run links to its DAG in Airflow, which opens in the
   matching folder.

## Consequences

- Operators and stewards see one hierarchy everywhere: the console
  catalog, Data sync, Job runs and the Airflow Dags page.
- Creating a repository creates its folders on the first deploy. Retiring
  a repository pauses its DAGs and archives the folder. It is not
  deleted, so run history stays.
- Airflow 3.4 is a recent release. M2 records the pinned patch and the
  test results. If a blocking defect appears, the fallback is the latest
  3.3 patch: the layout still works there and only the Folders panel is
  lost.
- Airflow's own access rules still apply to its UI. Folders are
  organisation, not authorization. Repo.io grants decide what a user
  sees in the console.
