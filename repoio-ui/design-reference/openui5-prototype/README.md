# repoio-openui5-prototype

> Status: **prototype** (design reference, not the product console)
> Milestone: enabler for M4 — the visual and interaction contract for the OpenUI5 console
> Owner domain: ui5

## Purpose

A clickable OpenUI5 prototype of the Repo.io console, built only from OpenUI5
1.136 (LTS) controls on the locked shell and theme: `sap.tnt.ToolPage` +
`ToolHeader` + `SideNavigation`, theme `sap_horizon` (Morning Horizon, ADR-0010), Arabic RTL
and English LTR. It shows how each approved page looks and behaves before M4
implements it against real APIs.

It deliberately does **not** call any backend. Every number, name and record
comes from `webapp/model/*.json` and is illustrative sample data
(CLAUDE.md §6 rule 2 applies to the product, not to this prototype). Do not
copy that data into `repoio-ui`.

## Pages

Layouts follow SAP Datasphere, drawn with OpenUI5 controls on the locked
Morning Horizon theme (ADR-0010). The kit's theme is unchanged; only the page layouts follow
Datasphere.

Scope is deliberately narrow for now: only Home, Domain management,
Connections (with CSV / Excel import), the Ontology Explorer, the Workflows
list, New workflow and Data jobs (job runs and run details) are designed. The domain detail, repository, data source, table and Explore pages were
removed at the owner's request; their code is in git history. Golden records
(list, record and lineage) were redesigned on 2026-11-16. Every other navigation item opens the planned-page placeholder.

Every table on the repository and table pages is a grid table (`sap.ui.table`: bordered resizable columns, column menu, row actions for navigation); the data preview grows with its panel when maximized and few columns share the full width. Tags follow SAP Fiori `sap.m.GenericTag` in a compact size: Tags follow one rule: a tag marks something worth a look, so a page with no problems has few tags.
- **KPI tags** (status stripe, label, value and unit) show measured values that have a threshold: quality and dimension scores, the empty share of a column only when it is 1 % or more, and the failed share of a check only when rows failed. A check that could not count rows (for example a file freshness check) shows a KPI tag in the error-handling state (*Not measured*).
- **Situation tags** (status icon and text) appear only for exceptions: failed and warning check results, dependent repositories that need attention, catalog card statuses. A passed check or a healthy status is a plain status text.
- **Classifications** (PII, sensitivity, glossary terms) are neutral markers or tokens, not situation tags, because they describe the column rather than a problem.

**Semantic colors** (SAP Fiori) come from one module, `webapp/util/semantic.js`; pages never pick a color for a status themselves.

| Semantic | ValueState | Means | Examples |
|---|---|---|---|
| Positive | Success | Good result or healthy normal state | published, deployed, live, succeeded, passed, stream running |
| Critical | Warning | The person looking at it should act | golden record needs review, key expiring, partial run, undeployed changes, gate needs review |
| Negative | Error | Failed or blocked | failed run or check, held in quarantine, gate stopped, access denied |
| Information | Information | In progress or waiting on someone else | running, scheduled, in review (approval queue), open change request |
| Neutral | None | No judgement | draft, unchanged, retired, expired, revoked on purpose |

Rules: management by exception (a normal record stays neutral); categories with no good or bad meaning (HTTP method, object type, PII, tier) never use a semantic color, they use neutral chips or indication colors that avoid red, orange and green; color is never the only carrier (text and icon always); ratings use `sapContent_RatedColor`, not Critical. Quality scores use one scale on every page (≥ 90 Positive, ≥ 75 Critical, below Negative); the thresholds belong to the data quality rule set and come from the API with the score, the prototype keeps a copy in `semantic.js`.

## Colors

Charts use a soft SAP chart palette (`BaseController.colors`). Custom CSS takes its colours from
the theme parameters (`var(--sapTextColor)`, `--sapBrandColor`, …), with the old values only as fallbacks.
Progress bars use light semantic fills (`css/style.css`), so status stays readable
without saturated blocks of color.
